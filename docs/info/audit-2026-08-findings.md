## What this document is, and what was NOT verified

- **Methodology.** The source workflow ran one *review* agent per unit
  (14 units → 97 candidate findings) and dual *verify* agents per finding.
  Because the workflow's synthesis step never completed, this document was
  built by parsing the raw journal (`journal.jsonl`), matching each verify
  result back to its finding by file/line and content overlap, and
  reconciling severity: **a finding is CONFIRMED unless every matching verify
  pass refuted it; a proposed severity is downgraded only when every verify
  pass that commented on severity agreed on the same lower value** — a single
  dissenting downgrade with the other pass silent keeps the original
  severity, flagged in that row's evidence. This differs slightly from a
  rougher first-pass count (4 critical / 10 high / 52 medium / 26 low) that
  was in circulation before this reconstruction; the table below (4 critical
  / 13 high / 53 medium / 25 low, after merging the 3 PEER_TOKEN duplicates
  into one row) is the one actually traced back to journal evidence.
- **7 of 97 findings had split verify verdicts** (one pass confirmed, one
  refuted or suggested a different severity). Each was individually resolved
  by reading both full verify transcripts, and in 2 cases (SeriesDetailPage.tsx
  evidence misattribution; a backfill script bug already fixed by commit
  `8051a3e` same-day) resolved as **REFUTED** — excluded from the table below.
  The other 5 were resolved CONFIRMED at the severity the stronger verify
  pass argued for.
- **Not independently re-run against live code**, except: the PEER_TOKEN
  tracked/public status above (checked directly via `git` and `gh`), and the
  two REFUTED items' resolution (checked directly against current file
  contents). Every other row's CONFIRMED status rests on the journal's
  verify-agent transcript, not a fresh independent check by this session.
- **Findings were not cross-checked against `KNOWN_ISSUES.md` exhaustively** —
  only a keyword pass against the critical/high list, which found no existing
  KI entry covering any of them. `KI-10` (create schemas not `.strict()`) is
  related-but-distinct from the medium `updateAccessorySchema` finding below
  (that one is an *update* schema, which KI-10's own text says is not
  supposed to happen) and is cross-referenced in that row.
- **Code may have moved since the audit ran.** The backfill-missing-covers.mjs
  REFUTED item above shows the audit and the repo can be out of sync by
  same-day commits; treat file:line as approximate for anything not
  re-verified.
